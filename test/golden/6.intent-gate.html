Request (verbatim)
In 3.1 plan_prefix is change of value, not type isn't it? * Validate it * If so, we need to update change category right? (chosen: New intent for per-kind change categories, then redo #3's gate)
Problem
The result gate labels every change with categories made for data-type fields: added, removed, renamed, type changed, nullability changed. Changes of other kinds don't fit, so they get the nearest wrong label: a constant whose value changed shows as a type change, a function whose behavior changed shows as a type change, and a moved doc section shows as a rename. The reviewer at the result gate reads a wrong description of what changed, which is the one thing the gate must get right. #1's, #2's, #3's, and #5's results were accepted with such labels; the changes themselves were right. The kind list has the same gap: skills, CLAUDE.md, and the design record have no kind of their own, so they were planned as non-semantic, though a change to a skill changes what every future agent does.
Acceptance criteria
  • Every change at a result gate is described by a category that says what actually changed, whatever the step's kind.
  • A change no category fits is shown as uncategorized, never forced into the nearest category.
Non-goals
  • Building the extractor that assigns categories automatically
    Why: Extraction is its own build-order step; until then categories are assigned by hand and labeled inferred.
  • Correcting the labels in #1's, #2's, #3's, and #5's accepted results
    Why: The new categories apply from #6 on; earlier results keep their labels (Q3, user, 2026-09-29).
Decided
Q0 Which kinds do prose changes get? Agent-facing instructions (skills, CLAUDE.md, hook prompts) change agent behavior; the design record is for humans; neither fits the code kinds, and both were planned as non-semantic (1.6, 1.7, 3.2, 3.3, 5.3).
Decided: instructions + docs: two new kinds. instructions: expect names the file and section, rules say what it now tells agents, and evidence is a dry run of the skill. docs: sections added, removed, or moved. non-semantic narrows back to typos, formatting, and pure moves.
Q1 What are the categories?
Decided: Shared list, subsets: one list (added, removed, renamed, moved, type changed, nullability changed, value changed, behavior changed, content changed); each kind declares which it can produce, as in the proposal. Validation rejects a category outside a kind's subset, and a change outside it shows as uncategorized.
Q2 Prose changes, like moved doc sections or a skill's new rule, don't have a before and after value. How should they show?
Decided: By what changed. Mechanical prose changes (moved, renamed, or a whole section added or removed) are table rows: What | From | To | Why. Wording changes (content changed, and behavior changed for instructions) are quoted, not tabled: one diff code block per change, - lines for removed and + lines for added text, with a line saying why. (User: if it's a simple or mechanical fix, a table is right; if sentences or paragraphs change, quote them as a code block.)
Q3 #1's, #2's, #3's, and #5's results were accepted with some wrong labels. What happens to them?
Decided: Leave them: the new categories apply from #6 on, and #1's, #2's, #3's, and #5's accepted results keep their labels. This drops #6's third acceptance criterion.
Q4 Q0 says instructions and docs steps name the file and section they change, but every expect entry must be a symbol: one token, no spaces, never a file path. How do prose steps name what they change?
Decided: New sections field: prose kinds get expect.sections: { doc, section }[]. doc is the skill name for a skill, or the repo-relative path for another file; section is the heading text. For prose the file is the identity, so a path is fine there. Code keeps the no-paths rule.
