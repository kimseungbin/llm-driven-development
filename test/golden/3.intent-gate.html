Decided
Q1 Scope: the prototype is solo and local (no server, accounts, web UI, search, or webhooks). The ldd docs design a team coordinator (NestJS, Postgres, web UI, forge adapters). Which one is the design?
Decided: Both, as two phases. The solo, local tool is the current phase. The team coordinator is the team-phase target and gets its own section. The data layer is designed now so the coordinator can adopt it unchanged.
Q2 Where do issues (intents and plans) live? The prototype keeps them in git refs in the product repo. The ldd docs keep them in the coordinator's database because issues can span repos and need deletion and per-item access control.
Decided: Git refs for now. A coordinator database may come in the future; that isn't decided.
Q3 Ref names: the prototype uses refs/plans/*, refs/plans-config, and a planned refs/reviews/*. The ldd docs put everything under refs/ldd/*. Which naming?
Decided: Move everything under refs/ldd/: refs/ldd/plans/<id>, refs/ldd/reviews/<id>, and refs/ldd/config. One refspec (refs/ldd/*) syncs all of it. Migrate the stored refs in one step.
Q4 Gates and the unit of review: the prototype has an intent gate, a plan gate, and a result gate for each step, with steps typed by kind. The ldd docs have a plan review and a change-level review built from items per layer (Decision, Contract, Behavior, Verification, Mechanical). Which model?
Decided: The three gates (intent, plan, result for each step), with steps as the unit of review. The ldd layers become step kinds: Contract becomes data-shape and signature-change, Behavior becomes behavior-change, Mechanical becomes non-semantic, Verification becomes each step's evidence, and Decision becomes the intent's decisions. In the team phase, a change is ready to merge when every step it implements has passed the result gate and nothing unplanned is left unresolved.
Q5 Who works out planned vs built? The prototype computes it deterministically from the observed diff and step expectations, and stores LLM judgments separately, labeled inferred. The ldd docs have the author's agent submit review items that map the diff to the intent, which the coordinator then checks.
Decided: Computed deterministically. Symbol lists are compared by machine; behavior and invariants are checked by the tests named in evidence or by the human; LLM judgments stay separate and labeled inferred. Agent-submitted review items are dropped, and the ldd coverage check becomes the unplanned bucket. Research and decision records written while working stay, attached to the intent and its steps.
Q6 Linking commits to plan data: the prototype uses a Plan-Step trailer, with one step per commit. The ldd docs use an Ldd-Work trailer that names a work session. Which one?
Decided: Plan-Step only. It links each commit to its step, which gives per-step diffs for reconciliation and the result gate. Research and decision records attach to step IDs from the plan gate onward. Ldd-Work is dropped.
Q7 Detecting stale plans: the prototype stores no base SHA, recomputes the base, and records the head SHA and observed-diff hash on each approval. The ldd docs store the commit the plan was made against and flag items that went stale against it. Which one?
Decided: Baseline on approvals, scoped by symbols. Plan content stores no SHA. A plan-gate approval records the main commit it saw; when main moves, only steps whose expected symbols changed go stale. A result-gate approval records the step's head SHA and observed-diff hash; the approval carries over if the recomputed hash is the same, and goes stale otherwise (like Gerrit change kinds and GitLab patch-ids).
Q8 Who can approve? The prototype lets an agent run approve when your message explicitly names the gate and rev, recorded as Via: agent, with SSH-signed approvals as a later option. The ldd docs require a passkey signature for any act that decides a gate, so no agent can approve.
Decided: By phase. Solo phase: CLI approve with delegated Via: agent approvals, as built now. Team phase: acts that decide a gate need a passkey signature, and delegated approvals never count toward a team gate. SSH-signed approvals are dropped in favor of passkeys.
Q9 Rendering: the prototype uses deterministic renderers per kind, and Claude never writes markup for records (your requirement). The ldd docs have agents write SVG diagrams, which are then sanitized. How do they fit together?
Decided: Deterministic renderers draw every record view, count, flag, and table. An architecture diagram is authored content attached to a decision: sanitized SVG, shown as-is, and labeled authored.
Q10 Git notes: the prototype rejected notes for plan data. The ldd docs use refs/notes/ldd only for a record, written after a merge, of how each merged commit was reviewed. Keep that record?
Decided: Drop it. The Plan-Step trailer links each merged commit to its step, and the step's ref holds the approvals.
Q11 Runtime: the prototype runs .ts directly on Node 26 with no dependencies. The ldd docs chose Bun everywhere, with NestJS on Bun for the coordinator. Which one?
Decided: Node 26 now, for the solo phase. The coordinator's runtime is decided later, in #4.
Q12 Design record format: the prototype keeps one long docs/design.md. The ldd docs are short nested files, one topic each, following your standing preference. Which format for the merged record?
Decided: Short nested docs: a docs/README.md index with 'Where we left off', a folder per area, and files of about 40 lines. CLAUDE.md points to the index. The merged record replaces docs/design.md and ~/repos/personal/ldd/docs, and ldd's docs are deleted once the merge is done.
