Problem

Acceptance criteria

  • The formats, their validation, and the authoring skills match every decision that changes a format.
  • The intent gate and plan gate layouts are each approved as a whole, after seeing them rendered on a real scenario.
  • The review-side questions are tracked in their own intent, so none of them get lost.

Decided
Q1 Who breaks an intent into steps and writes each step's expectations?
Decided: The agent proposes the steps and their expectations after reading the code, and the human approves, edits, or rejects them at the plan gate.
Q2 What's the list of step kinds, and does a step's risk come from its kind?
Decided: Start with five kinds (dto-shape, signature-change, behavior-change, feature, non-semantic) plus a fallback, open to adding more. If the list keeps growing, move to nested kinds. Risk is set per step, not derived from its kind.
Q3 How fine-grained is a plan: one step per logical change, or one step per field or symbol?
Decided: One step per logical change, whose expectations list every symbol it touches.
Q4 What shape do a step's expectations take, so they can be checked against what actually changed?
Decided: A fixed, validated shape per kind. Symbol lists (added, removed, changed from and to, unchanged) are checked by machine; rules and invariants stay prose, marked as checked by a test or the human. Anything machine-checked must be a symbol list, never prose. The fallback kind has no machine check.
Q11 A step's risk is now set per step, proposed by the agent. Does it need a stated reason?
Decided: A reason is required only for high-risk steps, but the agent records a one-line reason for every step. Views show high-risk reasons by default and hide the others until the reader turns them on.
Q5 How are relationships between intents recorded?
Decided: Typed links stored on one side only: blocks, duplicates, parent, plus the existing follow-up for deferred work. Links between steps of different intents go in the step's dependencies at the plan gate. Reverse links are computed, and a prose mention is just a mention.
Q6 How does a decision that needs someone else's confirmation get tracked, like Finance confirming the tax treatment?
Decided: It stays an open question owned by the outside party, and it blocks the intent until they confirm. Questions get an owner, which defaults to the approving human.
Q7 Should each acceptance criterion name the stakeholder need it serves?
Decided: Never. Acceptance criteria stay plain statements; the problem names who feels the pain.
Q8 What format are intents and plans written in: JSON only, or markdown with a structured header?
Decided: JSON only, written through the CLI. Markdown may be added later as an input the CLI converts.
Q9 The area list (fe, be, db, infra) doesn't fit every repo; this tool itself is a command-line tool that stores data in git. Should each repo define its own areas?
Decided: Each repo declares its own closed list of areas in a small config file, defaulting to fe, be, db, and infra. A setup skill helps create that config: it looks at the repo's layout, proposes an area list, and the human confirms it.
Q10 What's the third gate called?
Decided: The result gate. Its view badge becomes 'Result', and 'review' stays the word for what happens at every gate.
Q12 Plans already stored in refs use the current step format: #7 in the soft-delete repo, and this plan itself once its steps are written. Per-step risk and fixed expectation shapes change that format. Migrate the stored plans in place, or version the format and keep reading the old one?
Decided: Migrate in one step: switch to step format version 2 and migrate every stored plan in the same step. Stored plans are briefly unreadable between the code change and the migration, and that's accepted.
Q13 Where does a repo's area list live: a committed file in the product repo, or a ref next to the plans?
Decided: A ref next to the plans (refs/plans-config), written through the CLI with event history like plans. It works on repos you don't own. Revisit if areas ever gain path patterns.
Q14 The dto-shape kind (decided in Q2) covers any change to a data type's fields, not just data transfer objects: domain entities and the tool's own model too. Rename it?
Decided: Rename dto-shape to data-shape: a change to the fields of a data type (add, remove, rename, retype, or nullability), whatever role the type plays. Supersedes only the kind's name from Q2.
